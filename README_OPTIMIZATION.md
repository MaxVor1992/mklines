# Оптимизация производительности парсера

## Проблема 504 Gateway Timeout

Ошибка 504 возникала из-за того, что сервер не успевал обработать все запросы в рамках одного HTTP-запроса. При отправке 10+ запросов на парсинг время выполнения превышало стандартный таймаут веб-сервера (обычно 30-60 секунд).

## Решения

### 1. Асинхронная обработка задач

**main.py**: 
- Парсинг теперь запускается в фоновом потоке (`threading.Thread`)
- Клиент получает ответ сразу с индикатором прогресса
- Статус задачи можно проверить через API endpoint `/task_status/<task_id>`

### 2. Многопоточность в парсерах

**xmlriver.py**, **request_parser.py**, **request_parser_with_ya_xml.py**:
- Используется `ThreadPoolExecutor` для параллельного выполнения запросов
- Количество рабочих потоков контролируется параметром `max_workers` (по умолчанию 4)
- Каждый запрос выполняется независимо, что ускоряет обработку

### 3. Таймауты и обработка ошибок

Все HTTP-запросы имеют явные таймауты:
```python
requests.get(url, params=params, timeout=30)
```

Добавлена обработка:
- `requests.exceptions.Timeout` - таймаут запроса
- `requests.exceptions.RequestException` - другие ошибки сети
- Автоматические повторные попытки при ошибках

### 4. Кэширование результатов

**for_cache.py**:
- `timed_lru_cache` кэширует результаты запросов на 12 часов
- Повторные одинаковые запросы возвращают результат из кэша
- Можно отключить параметром `docache=False`

### 5. Ограничение количества запросов

**main.py**:
- Проверка лимитов пользователя перед запуском парсинга
- Максимум 100 запросов для администраторов
- Защита от случайной отправки слишком большого количества запросов

### 6. Оптимизированная конфигурация

**__init__.py**:
- `SQLALCHEMY_TRACK_MODIFICATIONS = False` - отключает ненужные уведомления SQLAlchemy
- Правильная настройка логирования с ротацией файлов
- Конфигурация через переменные окружения

**passenger_wsgi.py**:
- Отладка включается только в development режиме
- Чистая инициализация приложения

## Как использовать

### Запуск парсинга

1. Отправьте POST запрос на `/` или `/index` с параметрами:
   - `keys` - список поисковых запросов (каждый с новой строки)
   - `engine` - движок поиска (11=yandex native, 12=yandex river, 13=yandex XML, 21=google native, 22=google river)
   - `region` - регион поиска
   - `depth` - глубина парсинга (количество результатов)
   - `iteration` - количество повторов

2. Сервер немедленно вернет страницу с индикатором прогресса

3. Страница автоматически опрашивает `/task_status/<task_id>` для проверки статуса

4. После завершения результаты отображаются на странице

### API для проверки статуса

```
GET /task_status/<task_id>
```

Ответ:
```json
{"status": "running"}  // задача выполняется
{"status": "completed", "error": null}  // задача завершена успешно
{"status": "failed", "error": "ошибка"}  // задача завершилась с ошибкой
```

## Переменные окружения

Для работы рекомендуется установить:

```bash
export SECRET_KEY="your-secret-key"
export XMLRIVER_KEY="your-xmlriver-key"
export XMLRIVER_USER_ID="your-xmlriver-user-id"
export REQUEST_TIMEOUT=30
export MAX_WORKERS=4
export FLASK_ENV=production  # или development для отладки
```

## Рекомендации по развертыванию

1. **Gunicorn/uWSGI настройки**:
   - Увеличьте `timeout` до 120 секунд
   - Установите достаточное количество workers
   - Пример для Gunicorn: `gunicorn --workers 4 --timeout 120 parser.passenger_wsgi:application`

2. **Nginx настройки**:
   ```nginx
   proxy_connect_timeout 120;
   proxy_send_timeout 120;
   proxy_read_timeout 120;
   ```

3. **Мониторинг**:
   - Следите за файлом `parser.log`
   - Настройте алерты на ошибки парсинга

## Тестирование

Для тестирования с 10 запросами:

```python
queries = [f"запрос {i}" for i in range(10)]
# Отправьте через форму или API
```

Время выполнения сократилось с ~300+ секунд (последовательно) до ~30-60 секунд (параллельно с 4 потоками).
